# Information-flow diagnostic — 31 October 2026

> Historical baseline before repairs. For the current implementation and open release gates, see `docs/implementation/INFORMATION_FLOW_FIX_PLAN.md`.

## Scope and result

This is a targeted diagnostic, **not a live, end-to-end deployment certification**. It traces and exercises representative fall, medicine, family-message, task and call paths. It does not cover all 83 Edge Functions or every screen.

Run `corepack pnpm run test:information-flow`. At the audited commit the result is **11 tests: 1 passes, 10 fail**. At that baseline the diagnostic exited nonzero. The follow-up repair added it to `corepack pnpm test`; consult the fix plan for current results and remaining gaps. These are behavioural checks, not a static-only suite. `tests/integration/information-flow-diagnostic.test.mjs` runs actual app action/mapper and Edge Function code, with the existing PostgREST/auth doubles. For the fall-status and message-type writes, PGlite executes PostgreSQL constraints extracted from the migrations. It does **not** apply the full schema or reproduce Supabase RLS, Storage, Realtime, network delivery or a phone. The grandchild test extracts the app's literal message type and passes it to the real handler; it does not run the whole grandchild UI.

Baseline `corepack pnpm test` passed: 550 edge tests; RLS, function coverage, test-substance and docs audits passed. `corepack pnpm run test:e2e` passed its iPhone HTML smoke test. A separate existing check, `node --test tests/e2e/vnext-flows.test.mjs`, fails immediately with `ENOENT` for `apps/elder/src/state/consentPacks.ts`. `scripts/ci/verify-browser.sh` calls that check. The default test chain does not.

No live Supabase project, credentials, Docker daemon or physical phone was available in this workspace. No actual family notification, 112 call, camera, push token, video media or deployed policy was exercised. In particular, a successful simulated notification-record write would not by itself prove push delivery.

## Findings, ordered by impact

### P0 — Do not rely on the emergency controls or fall escalation for safety

1. **Fall escalation cannot claim the row under the migrated enum.** The real handler writes `processing` and suppresses the resulting claim error as though another worker had claimed it (`supabase/functions/fn-fall-escalation/index.ts:68-75`). `fall_status` contains only `possible`, `confirmed`, `false_alarm`, `no_response`, and `resolved` (`supabase/migrations/20260614000000_vnext_wellrounded_patch.sql:92`). The diagnostic runs the real handler with PostgreSQL checking the write: PostgreSQL returns `22P02`, zero falls are processed, and no family notification is inserted. The handler also writes `family_alerted`, which is likewise absent from that enum. Existing tests use a database double that does not enforce the enum (`tests/edge/fn-fall-escalation-behaviour.test.mjs`).
2. **“Help needed” gives a false assurance.** The app queues a negative fall-confirmation response then displays a message saying family and emergency services are alerted (`apps/elder/src/hooks/useHavenActions.ts:204-209`, `packages/i18n/locales/en-GB.json`, `packages/i18n/locales/nl-NL.json`). `fn-pending-confirmation-respond` resolves the confirmation but has no false-resolution fall notification branch (`supabase/functions/fn-pending-confirmation-respond/index.ts:86-106`). The diagnostic observes no immediate family notification. Another mechanism could in principle act later, but finding 1 blocks this fall escalator and no emergency-services dispatch was established here.
3. **Emergency and crisis buttons claim progress without carrying it out.** `EMERGENCY`, `CALL_FAMILY`, and `CRISIS` only show alerts in `apps/elder/src/hooks/useHavenActions.ts:30-32,70-72`. The diagnostic presses `EMERGENCY` and finds no dial action or actionable alert button. The crisis copy says family is alerted even though that branch performs no notification (`packages/i18n/locales/en-GB.json`). This finding concerns those buttons, not every other crisis path in the app.
4. **Additional escalation design hazards require investigation before repair.** The latest `get_active_emergency_falls` definition returns `no_response` (`supabase/migrations/20260620000002_end_to_end_runtime_fixes.sql:266-292`), but the handler's claim filter only accepts `possible` and `processing`. It also accepts `processing` in a claim without checking staleness (`supabase/functions/fn-fall-escalation/index.ts:68-75`), so concurrent workers may both claim the same processing row if the enum is repaired. Adding enum values alone would not establish a safe escalation workflow. `tts-cache` permits only audio (`supabase/migrations/20260611000002_storage_rpc_security.sql:13`) but the handler uploads emergency-location JSON there (`supabase/functions/fn-fall-escalation/index.ts:119-128`); Storage behaviour needs a live check.

### P0/P1 — Medication identity and confirmation

5. **A Dutch elder's dose tap does not create the confirmation.** The real app sends English `I took it` (`apps/elder/src/hooks/useHavenActions.ts:219-221`). The real endpoint uses the elder profile locale in preference to the request locale (`supabase/functions/fn-voice-pipeline/index.ts:96-97`) and classifies Dutch and English with separate patterns (`supabase/functions/fn-voice-pipeline/index.ts:11-32,273`). The diagnostic invokes the action against the handler: `nl-NL` produces no confirmation; `en-GB` produces the targeted confirmation.
6. **The app says “taken” before repeat-back is answered.** The same app branch ignores the returned voice result and displays `actions.take_success.alert`; the endpoint returns `AWAIT_REPEAT_BACK` (`supabase/functions/fn-voice-pipeline/index.ts:301-324`). The diagnostic verifies a confirmation exists while the app displays the success key. A pending confirmation is not a recorded dose.
7. **Invalid targeted dose may be replaced with another dose.** `supabase/functions/fn-voice-pipeline/index.ts:285-303` falls back to the earliest open reminder if the supplied ID is not found. The diagnostic sends a different ID and observes a confirmation for the existing reminder. If answered, that could associate the answer with a dose other than the one selected.

### P1 — Messaging and calls

8. **Grandchild hello fails its database constraint.** `apps/grandchild/App.tsx:118` sends `text`; `fn-grandchild-message-send` passes it through (`supabase/functions/fn-grandchild-message-send/index.ts:30`), but the schema permits `tekst`, `voice_note`, `foto`, `video_hallo`, or `tekening` (`supabase/migrations/20260611000001_haven_v121_production_schema.sql:337`). The handler/PG-constraint diagnostic returns `23514` and HTTP 500 rather than inserting the message.
9. **Unread messages appear read.** `fn-screen-data` does not select `read_by_elder` (`supabase/functions/fn-screen-data/index.ts:48`), and the mapper hardcodes `unread: false` (`apps/elder/src/services/screenDataMapper.ts:103-115`). The diagnostic gives the real mapper an unread row and observes `false`. The home badge and message indicator therefore cannot reflect unread state. No writer for `read_by_elder` was found in the app or Edge Functions during this review; read-receipt behaviour needs a proper authorised implementation.
10. **Calls have no established incoming flow; decline request is malformed.** The family dashboard creates a session (`apps/family/src/components/CallButton.tsx:28-55`), while `ElderScreen` never supplies `incomingCall` to its renderer (`apps/elder/src/screens/ElderScreen.tsx:95-117`) and no elder subscription to `video_call_sessions` was found. Separately, the decline action sends `session_id` (`apps/elder/src/hooks/useHavenActions.ts:141-157`), but the endpoint requires `video_call_session_id` (`supabase/functions/fn-video-call-end/index.ts:13`); the diagnostic observes HTTP 400, the session remaining `created`, and the app nevertheless showing its decline alert. Actual audio/video media and background ringing were not tested.

### P2 — Other incomplete paths and test coverage

11. **Task completion is inert.** The renderer emits `TOGGLE_TASK:<id>` (`apps/elder/src/renderer/ScreenRenderer.tsx:308`), but `useHavenActions` has no branch for it and falls back to a screen-data read (`apps/elder/src/hooks/useHavenActions.ts:260-268`). The diagnostic observes no write or queue action.
12. **Onboarding consent data is not connected.** `renderOnboarding` expects `pendingConsentPack` (`apps/elder/src/renderer/ScreenRenderer.tsx:701-730`) but `ElderScreen` supplies neither that field nor the counts (`apps/elder/src/screens/ElderScreen.tsx:95-117`). `fn-consent-pack-list` exists, but no app caller was found. This is a source-trace finding, not a completed live onboarding test.
13. **Browser verification is not green.** The existing `tests/e2e/vnext-flows.test.mjs:26,40` reads a deleted `apps/elder/src/state/consentPacks.ts` and fails before its tests run; `scripts/ci/verify-browser.sh:23` invokes it. The successful default suite does not run this script (`package.json`).

## Remediation plan and done criteria

| Step | Rubric for done |
|---|---|
| Emergency and fall | Emergency UI makes only truthful claims and provides a usable, consent-appropriate urgent action; fall claims use valid durable state, atomic concurrency control and crash recovery; negative answers have explicit tested escalation semantics. Real PostgreSQL, concurrent workers, failed delivery, and device/push tests pass. Obtain clinical/product review before relying on it. |
| Medication | A tap names exactly one authorised open reminder in both languages and online/offline; missing/stale/foreign IDs fail closed; no successful-recording message precedes the actual durable confirmation. Exercise app → endpoint → database → refreshed UI. |
| Family messages | Stored type vocabulary agrees across app/API/schema; message creation, notification, unread state and authorised read receipts work in both directions on real RLS policies. |
| Calls | Create, ring, decline/end, time out and answer work across both applications, including background/foreground transitions and configured real media; API errors are surfaced. Do not claim a video call until media is established. |
| Other UI | Tasks persist or honestly report failure; onboarding reads and saves actual consent state; stale source-only browser checks are replaced with executable behavioural checks. |
| Release gate | The diagnostic and default suite pass; full migrations, RLS and storage are exercised on Supabase; browser and physical-device journeys, provider delivery and failure modes are independently verified. |

These are findings and test assets only. No production remediation is included in this diagnostic branch.
